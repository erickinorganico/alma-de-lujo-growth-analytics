<interfaces>
`scripts/package_release_v1.py` exposes two exact modes. `preflight --ref COMMIT --output ZIP --checksum PATH` builds the deterministic ZIP/checksum for CI without creating or claiming a publication acceptance sidecar. `release --ref v1.0.0 --output .local/releases/Alma_OS_v1.0.0.zip --checksum ... --acceptance ... --ci-sidecar .local/release-evidence/v1.0.0-ci-reproducibility.json` builds the same ZIP from the tag and writes the external acceptance sidecar only after the canonical SHA-A CI proof exists. Both modes build from a fresh `git archive` of that exact ref, call the Phase 4 public-kit builder in the archive, require the exact committed Phase 5 workbook hashes/receipts and normalize ZIP order, paths, permissions and timestamps. They write an inner `acceptance-summary.json` that excludes the outer ZIP hash. `scripts/audit_release_v1.py audit-preflight --zip ZIP --checksum PATH --manifest client/v1/release-manifest.json --require-version 1.0.0` performs the CI-safe extracted package, license, privacy and link audit without pretending publication occurred.

The external acceptance sidecar is intentionally not a tracked input to the tagged commit: it records the final ZIP hash, the inner release-manifest hash and the ignored same-SHA CI sidecar hash without creating a self-reference. It is a release asset alongside the ZIP and `.sha256`. The tracked `client/v1/acceptance-summary.json` contains deterministic gate identities, committed receipt hashes, limitations and EXT states but no mutable CI run IDs, private paths, task response bodies or outer archive hash. The inner `release-manifest.json` never lists or hashes itself: its `entries` cover every other ZIP member, the auditor requires `member_set = entries + {release-manifest.json}`, and only the outer ZIP hash plus external acceptance sidecar bind the manifest bytes.
</interfaces>
